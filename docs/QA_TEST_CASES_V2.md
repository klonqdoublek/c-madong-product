## 1. วัตถุประสงค์

เอกสารฉบับนี้เป็นชุดกรณีทดสอบแบบย่อ โดยคัดจากเอกสารทดสอบฉบับเต็มให้เหลือเฉพาะกรณีที่จำเป็นและเป็นพื้นฐานมากที่สุด เพื่อใช้ประกอบการเขียนเล่มปริญญานิพนธ์ให้กระชับ อ่านง่าย และสะท้อนการทดสอบฟังก์ชันหลักของระบบ C-Madong

## 2. หลักเกณฑ์การคัดเลือก

เลือกเฉพาะ test case ที่ตรงกับ 5 ประเด็นหลัก ดังนี้

1. ฟังก์ชันหลักที่ผู้ใช้ใช้งานจริงบ่อย
2. การตรวจสอบข้อมูลนำเข้าเบื้องต้น
3. การกำหนดสิทธิ์และการป้องกันการเข้าถึงข้อมูล
4. การเชื่อมต่อระหว่างโมดูลสำคัญของระบบ
5. การใช้งานบนหน้าจอมือถือซึ่งเป็นบริบทหลักของระบบ

จากเอกสารฉบับเต็มจำนวน 117 กรณีทดสอบ ได้คัดเหลือ 20 กรณีทดสอบ สำหรับใช้เป็นตัวแทนของการทดสอบระบบในเล่ม

## 3. ขอบเขตที่ใช้ในฉบับย่อ

| กลุ่มการทดสอบ | เหตุผลที่เลือก |
|---|---|
| Authentication & Onboarding | เป็นจุดเริ่มต้นของทุกการใช้งาน |
| Maintenance | เป็น workflow หลักของระบบสำหรับนิสิตและเจ้าหน้าที่ |
| Announcements | เป็นฟังก์ชันสื่อสารหลักของหอพัก |
| AI Chatbot & RAG | เป็นฟีเจอร์เด่นของระบบและเกี่ยวข้องกับข้อมูลผู้ใช้ |
| Billing & Parcels | เป็นบริการหลักที่นิสิตใช้งานจริง |
| Security & RBAC | ใช้ยืนยันว่าระบบป้องกันสิทธิ์การเข้าถึงได้ |
| Usability | ใช้ประเมินความพร้อมในการใช้งานจริงบนมือถือ |

## 4. Essential Test Cases

> หมายเหตุ: ในเล่มสามารถใช้ตารางนี้ได้ทันที และหากมีผลทดสอบจริงค่อยเพิ่มคอลัมน์ `Actual Result` และ `Status` ภายหลัง

### 4.1 Authentication & Onboarding

| Ref. | Test Case | Steps โดยย่อ | Expected Result | Type |
|---|---|---|---|---|
| TC-A01 | Login ผ่าน LINE สำเร็จสำหรับผู้ใช้ที่มีข้อมูลครบแล้ว | เปิดหน้า login → เข้าสู่ระบบด้วย LINE | ระบบสร้าง session และพาไปหน้า dashboard | Positive |
| TC-A04 | Register ด้วยรหัสนิสิตไม่ถูกต้อง | กรอก student ID ไม่ครบตามรูปแบบ → submit | ระบบแสดง validation error และไม่บันทึกข้อมูล | Negative |
| TC-A07 | Onboarding สำเร็จเมื่อเลือกข้อมูลห้องและเตียงครบ | เลือกตึก ชั้น ห้อง เตียง และข้อมูลที่จำเป็น → submit | ระบบบันทึกข้อมูลสำเร็จและพาไป dashboard | Positive |
| TC-A09 | ผู้ใช้ที่ยัง onboarding ไม่เสร็จเข้าหน้า dashboard โดยตรง | เปิด URL dashboard โดยไม่ทำ onboarding ให้ครบ | ระบบ redirect ไปหน้า onboarding | Security |

### 4.2 Maintenance

| Ref. | Test Case | Steps โดยย่อ | Expected Result | Type |
|---|---|---|---|---|
| TC-M01 | นิสิตส่งคำร้องแจ้งซ่อมสำเร็จ | กรอกข้อมูลครบ อัปโหลดรูป แล้ว submit | ระบบบันทึกคำร้องสำเร็จและตั้งสถานะเริ่มต้นถูกต้อง | Positive |
| TC-M02 | ส่งคำร้องโดยไม่เลือกหมวดหมู่ | เว้นค่า category แล้ว submit | ระบบแจ้งข้อผิดพลาดและไม่บันทึกข้อมูล | Negative |
| TC-M11 | นิสิตเห็นเฉพาะรายการแจ้งซ่อมของตนเอง | เปิดหน้า maintenance ด้วยบัญชีนิสิต | ระบบแสดงเฉพาะ ticket ของผู้ใช้ปัจจุบัน | Security |
| TC-AM04 | เจ้าหน้าที่เปลี่ยนสถานะ ticket แล้วระบบแจ้งเตือนต่อเนื่อง | เปิด ticket จากฝั่ง admin → เปลี่ยนสถานะ | สถานะถูกอัปเดตและมี notification ไปยังนิสิต | Integration |
| TC-AM09 | ผู้ไม่มีสิทธิ์ไม่สามารถแก้ไข ticket ผ่าน API ได้ | เรียก API update ticket ด้วย role ที่ไม่เกี่ยวข้อง | ระบบตอบกลับ 403 และไม่เปลี่ยนข้อมูล | RBAC |

## 6. ตัวอย่างข้อความสำหรับใส่ในเล่ม

> ในการทดสอบระบบ C-Madong ผู้พัฒนาได้ออกแบบกรณีทดสอบจาก requirement และ user flow ของระบบทั้งหมด จากนั้นคัดเลือกเฉพาะกรณีทดสอบพื้นฐานที่มีความสำคัญต่อการใช้งานจริง เพื่อนำเสนอในเล่มปริญญานิพนธ์ โดยชุดทดสอบฉบับย่อนี้ประกอบด้วย 20 กรณีทดสอบ ครอบคลุมการเข้าสู่ระบบ การลงทะเบียน การแจ้งซ่อม การจัดการประกาศ การใช้งาน AI Chatbot การเข้าถึงข้อมูลบิลและพัสดุ การกำหนดสิทธิ์ผู้ใช้ และการใช้งานบนอุปกรณ์เคลื่อนที่ ซึ่งช่วยสะท้อนให้เห็นว่าระบบสามารถรองรับการทำงานหลักได้อย่างถูกต้องและปลอดภัยในระดับพื้นฐาน

- หากต้องการใส่ผลการทดสอบจริงในภายหลัง แนะนำเพิ่มคอลัมน์ `Actual Result`, `Status` และ `Remark`
